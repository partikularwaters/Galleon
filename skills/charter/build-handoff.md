# Hand off a build, feature, fix, or solution

Use this guide when the plan will implement application behavior. Identify the
project's development workflow or relevant implementation skill, and prepare
enough design and evidence for that executor to begin without inventing decisions.
Keep contract discovery and authorization under SKILL.md's common rules.

## Prepare the implementation route

Name the intended behavior and its inputs, defaults, and acceptance conditions.
Identify code and test owners, existing interfaces, and preserved behavior. Give
each material implementation step its dependency, permitted edits, result home,
checks, and stopping condition. Use the project's conventions and planning form.

When an implementation skill is available and relevant, read its actual contract
and only the resources this build needs. Otherwise an explicit project development
procedure can own execution. State the selected procedure and its source. Do not
substitute a Galleon structural method for application implementation: Scaffold
establishes agreed project structure and does not execute the first application job.

Use Galleon methods for additional responsibilities only when the plan calls for
them. Delegate prepares written work items for a larger approved plan; Survey
reviews an actual result against its agreement; Remember captures verified state
at existing owners. Prepare each selected method's inputs and preserve its boundary.
Routine build tests remain part of implementation without requiring a separate
review or audit ceremony.

## When the build also needs structure

If planning reveals missing project contracts, record owners, or a context mapping,
use [structure handoff](structure-handoff.md) for those specific operations.
Include their exact creation list or mapping and checks in the build plan, and
state whether implementation depends on them. Distinguish structural setup from
the application work that follows it. Keep existing sufficient arrangements.

A build's ordinary source and test files follow its development workflow. Their
creation alone does not justify a Scaffold phase or a new project architecture.

## Present the next action

Name the same coding agent as executor unless the request or project workflow
assigns someone else. State the first eligible implementation step, its inputs,
and the required authorization. If structural setup is a real dependency, name
that step first and explain how the build resumes afterward.

After execution is authorized, leave Charter and follow the named development
workflow or implementation skill. Recheck current code and dependencies, perform
the approved changes and tests, and report the observed result. A new design
decision or broader scope returns to planning. Follow the project's review and
acceptance rules without treating passing tests as human acceptance.

## Small example

A synthetic parser already has code, tests, and a planning owner. The proposal
adds an opt-in trimming argument while preserving the default output. Its handoff
names the existing development procedure, the two permitted code/test files,
the default and opt-in output checks, and this agent as executor after authorization.
No structural method is needed. If verified continuation is requested, Remember
can capture the actual result at the established owner afterward.
This is proposed behavior, not an observed project run.
