# Hand off project structure and context movement

Use this guide when the plan changes where project context, contracts, records,
or responsibilities live. Translate the arrangement into exact operations before
presenting it for approval. Keep contract discovery and authorization under
SKILL.md's common rules. A proposed file tree alone does not finish the plan.

## Select methods by the operation

This vocabulary identifies candidate responsibilities. Verify selected available
contracts and their required inputs while planning. Include only the steps the
project needs, in dependency order.

| Operation | Method and boundary | Prepare in the plan |
| --- | --- | --- |
| Create missing project structure | `scaffold`: agreed creations, without overwrite or executing the first job | Exact target, creation list, contents, collision checks, and recovery. |
| Reorganize existing context | `import`: apply an agreed mapping while preserving content, ownership, and references | Source-to-destination mapping, owners, allowed edits, consumers, baseline, and preservation/recovery checks. |
| Turn a larger agreed plan into written work items | `delegate`: write bounded handoffs, without implementation or session dispatch | Dependencies, work-item home, inputs, scope, checks, and result locations. |
| Review an actual result against its agreement | `survey`: report evidence and defects, without repair or acceptance | Selected plan, actual result, relevant baseline, permitted checks, and report home. |
| Save verified state for continuation | `remember`: capture at existing owners, without designing memory or restoring work | Capture procedure, record owners, verified results, decisions, and next action. |
| Correct navigation from existing facts | `sync`: fix links and descriptions, without inventing owners, rules, or status | Routing scope, authoritative targets, permitted corrections, and regeneration rules. |
| Assess whether a structure supports a named job | `audit`: bounded observation, without live repair or acceptance | Named promise, representative job, owners, permitted inspection or disposable checks, and evidence limits. |
| Explain an observed failure | `diagnose`: evidence-backed diagnosis and proposed response, without repair or reset | Expected and observed behavior, relevant files, baseline, evidence, and permitted reproduction. |

Scaffold cannot move existing records. Import cannot redesign an approved mapping.
Sync cannot settle new ownership. Audit tests a structure's promise, while Survey
reviews a particular result. A diagnosis can identify a repair to plan, but does
not carry it out. These distinctions determine the route for a request such as
"organize the project."

## Prepare application of the arrangement

Show the exact creation contents, context mapping, or navigation corrections.
For adapted forms, replace Galleon library references with project-owned routes
and procedures, remove template-author guidance, and check links from the intended
location. Include enough operational detail for the agreed job to proceed without
the original library; naming a skill alone does not supply that procedure.
Name existing owners and the authority for any proposed ownership change. Identify
consumers and affected references before movement. Separate creations from edits
or retirement of existing content; each needs its own permitted scope and checks.
Preserve unrelated work and choose recovery proportionate to the operation.

For each material step, name its method or explicit project procedure, inputs,
dependencies, allowed changes, result home, checks, and stopping condition. If a
selected bundle is unavailable, disclose the unread contract and use the common
rules in SKILL.md to identify a covered project procedure or open execution choice.
Do not postpone a creation list or mapping until the executor must invent it.

Give a named promise its own bounded observation when that promise matters.
Checking links establishes target existence; a claim that a fresh session can
find the job requires actual fresh-session evidence. Successful structural setup
does not establish successful application work, restoration, or human acceptance.

## Present the next action

Name the same coding agent as executor unless the request or project workflow
assigns someone else. Identify the first eligible structural step and any required
authorization. After execution is authorized, leave Charter and follow the named
method, rechecking current destinations, sources, and dependencies before writes.
Stop under its contract for a collision, drift, or a need to redesign the mapping.

If application work follows setup, name that as a separate handoff using
[build handoff](build-handoff.md). Scaffold does not automatically start that job.
Both phases need declared scope and dependencies; one phase's checks do not
authorize an unspecified next phase.

## Small examples

A synthetic project needs a durable task route. The plan specifies two missing
files and their contents. This agent uses Scaffold after authorization, verifies
the contents and links, then uses Remember under the newly established capture
procedure. An occupied destination stops Scaffold before writing and returns
the specific conflict to planning.

A synthetic project retains useful record owners but has stale router links.
The plan selects Sync and supplies authoritative targets and permitted corrections.
Import belongs in the handoff only when an approved mapping actually moves or
copies existing context. A requested navigation promise can then receive a
bounded Audit with its own named job and evidence limits.
These examples describe proposed behavior, not observed project runs.
