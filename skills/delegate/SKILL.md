# Delegate

One job: Make written work items from an agreed plan.

First read the project's entry instructions and relevant records. Find the owner
of this job and inspect the current files; check Git status when Git is available.
Read only what the task needs. Existing project rules and human authorization govern
scope. A skill invocation is not permission to overwrite files or invent approval.

If an important boundary is missing, explain it in plain language, give a small
concrete example, describe the benefit and tradeoff, and offer proportionate choices.
Use existing homes and rules when they suffice. Do not stop repeatedly for decisions
already covered by the current agreement. Resolve unclear authority before consequential
writes. Keep proposed behavior, observed checks, and accepted work distinct.

1. Identify the selected plan, dependencies, current eligibility, and existing work-item home. If no home exists, provide a chat draft or propose one.
2. Give each item its purpose, inputs, allowed changes, checks, stopping rules, and useful result location. Preserve the plan’s boundaries.
3. Keep tightly coupled work together. Use leaner items for established patterns and larger items for first-pattern work. Order dependent work explicitly.
4. Distinguish ready work from blocked work. Return written handoffs; do not choose models, launch sessions, or send messages unless separately authorized.

Boundaries: Implementation, redesigning the plan, accepting results, or silently changing project status.

## Project inputs and conditional resources

Always resolve the selected agreed plan, actual dependency state, work-item owner, specifications, and allowed changes.
Use the project's existing contract and forms first. If they adequately cover the
job, skip Galleon's alternative templates and work within those boundaries.

| When | Read | Use it to |
| --- | --- | --- |
| Written work items are needed and no adequate local form exists | [work item](_templates/work-item.md) | Provide complete inputs, boundaries, checks, and handoffs. |
| A concrete handoff illustration would clarify the proposal | [date label handoff](examples/date-label-handoff.md) | Show a complete bounded item without inventing dependencies. |

Do not load unrelated evidence or create a dispatch/model-selection procedure.
Read only relevant sections and examples. Adapt optional forms at existing owners;
a bundled resource does not grant write authority or replace a project agreement.
