# Diagnose

One job: Explain a failure before proposing a repair.

First read the project's entry instructions and relevant records. Find the owner
of this job and inspect the current files; check Git status when Git is available.
Read only what the task needs. Existing project rules and human authorization govern
scope. A skill invocation is not permission to overwrite files or invent approval.

If an important boundary is missing, explain it in plain language, give a small
concrete example, describe the benefit and tradeoff, and offer proportionate choices.
Use existing homes and rules when they suffice. Do not stop repeatedly for decisions
already covered by the current agreement. Resolve unclear authority before consequential
writes. Keep proposed behavior, observed checks, and accepted work distinct.

1. Identify expected and observed behavior, relevant files, and available evidence. Reproduce only within permitted disposable scope, or state why reproduction is unavailable.
2. Separate confirmed facts, inferred causes, and unresolved hypotheses. Check whether later changes make recovery unsafe.
3. Propose the smallest supported response with affected paths, preservation, and checks. Do not recommend a reset merely because the task is difficult.
4. Return the diagnosis and next useful action. Follow the project’s repair authorization rather than applying the proposal during diagnosis.

Boundaries: Repairing content, resetting Git, guessing recovery, inventing acceptance, or launching sessions.
