# Conditional arrangement for distinct responsibilities

Read only when repeated jobs have genuinely different planning, execution, and
review owners, and the agreed setup selects this arrangement. A small job rarely
needs it. This is a design option, not a compulsory Galleon agency or lifecycle.

```text
project/
  AGENTS.md
  CONTEXT.md
  planning/
    CONTEXT.md
    selected-job.md
  work/
    CONTEXT.md
    selected-job.md
  memory/
    CONTEXT.md
```

Keep code and existing records at their native homes. Omit any surface whose job is
already covered. Existing task agreements, approvals, and evidence can remain in one
record or linked owners; no acceptance header, engine, journal, or status schema is
required by this example. Memory can route to existing state instead of copying it.

## Explain each retained owner

Planning owns the agreed purpose, scope, inputs, and checks. Work owns executed
changes and result evidence. Memory owns the procedure for saving and restoring
state, while the state itself can live elsewhere. The root routes to these owners;
it does not repeat their contents. The project's actual approval rules govern each
handoff, and a favorable review does not invent human acceptance.

Benefit: different readers can find the agreement or evidence relevant to their job.
Cost: more records and routes require maintenance. One task record may cover the
same needs for a small team; show that alternative before proposing this layout.

## Apply only the chosen setup

Scaffold checks agreed missing targets and contents, then creates only those paths.
This resource does not authorize application, overwriting, or creation of every
listed folder. Changes to existing homes need a separate preservation mapping.
Do not create empty speculative jobs or operation directories. Verify created links,
owners, and contents; setup alone does not prove independent usability or restoration.
