# Survey

One job: Explain what a result demonstrates.

First read the project's entry instructions and relevant records. Find the owner
of this job and inspect the current files; check Git status when Git is available.
Read only what the task needs. Existing project rules and human authorization govern
scope. A skill invocation is not permission to overwrite files or invent approval.

If an important boundary is missing, explain it in plain language, give a small
concrete example, describe the benefit and tradeoff, and offer proportionate choices.
Use existing homes and rules when they suffice. Do not stop repeatedly for decisions
already covered by the current agreement. Resolve unclear authority before consequential
writes. Keep proposed behavior, observed checks, and accepted work distinct.

1. Identify the plan or agreed task, actual result, relevant baseline, permitted checks, and report owner. A chat report is sufficient when no saved report is required.
2. Compare actual changes with the scope. Review partial work honestly. Run only authorized checks and report failures, interventions, and relevant environment details.
3. Separate direct observations from supplied reports, fixtures, and unavailable evidence. Passing automated checks does not prove independent use or every promise.
4. Report actionable defects, supported claims, and limits. Recommend the next response without accepting its own evidence or changing status.

Boundaries: Repairing the result, restructuring, originating approval, or advancing project status.
